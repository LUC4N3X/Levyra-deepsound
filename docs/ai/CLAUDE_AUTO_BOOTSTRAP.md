# Claude Code automatic tooling bootstrap

Levyra keeps Claude Code project tooling automatic and fail-open after the native
project surface is active. Canonical Claude configuration is tracked under
`.agents/claude/`, shared Levyra skills are tracked only under `.agents/skills/`,
and the native `.claude/` directory is an ignored local projection generated by
`scripts/sync_agent_runtime.py`.

The existing Claude `SessionStart` environment probe and prompt-routing hooks
stay in place; this layer also exposes the project-scoped jCodeMunch MCP without
replacing Claude's native repository tools.

## Projection bootstrap

The deterministic first projection is:

```bash
python3 scripts/sync_agent_runtime.py --runtime claude --quiet
```

The normal `scripts/setup-ai.ps1` and `scripts/setup-ai.sh` commands run that
projection for Claude and Codex together.

A clean clone also exposes `.mcp.json` before `.claude/` exists. When Claude
approves and launches the project-scoped jCodeMunch server,
`scripts/claude-jcodemunch-mcp.sh` performs a best-effort Claude projection
before starting jCodeMunch. This is an additional bootstrap path, not evidence
that an already-running Claude process retroactively loaded files created after
its project inventory was built.

If `.claude/` first appears during a running session, start a new Claude session
before treating projected instructions, settings, agents, rules, or skills as
discovered.

## Automatic behavior after projection

On `startup` and `resume`, projected `.claude/settings.json` invokes canonical
hooks under `.agents/claude/hooks/`:

1. the projection refresh runs first and keeps the native surface synchronized;
2. the Levyra environment hook checks RTK and the local toolchain;
3. `.agents/claude/hooks/jcodemunch-start.sh` ensures the pinned jCodeMunch
   runtime via the shared `scripts/codex_jcodemunch.py` launcher and refreshes
   the Levyra index;
4. `.mcp.json` exposes that same pinned runtime to Claude as the project-scoped
   `jcodemunch` MCP server;
5. projected `.claude/settings.json` allows `mcp__jcodemunch`, so individual
   jCodeMunch tool calls do not require repeated permission prompts;
6. `UserPromptSubmit` invokes the canonical Levyra skill router, while Claude
   discovers projected `.claude/skills/` directly from `.agents/skills/`.

Claude should prefer jCodeMunch for targeted symbol-level discovery, then use
native Read/Grep/Glob/Bash whenever broader context is necessary for control
flow, lifecycle, concurrency, state, generated behavior, tests, or correctness.
Token savings never override correctness.

## First project approval

Claude Code requires approval before using a project-scoped MCP server from
`.mcp.json`. Levyra does not bypass that security decision. After the project
server is approved, normal jCodeMunch tool calls are covered by the generated
`mcp__jcodemunch` project permission.

If the MCP install, index, server launch, or best-effort projection fails, Claude
continues with its native repository tools. Failure must not block coding or be
treated as permission to weaken sandboxing or validation.

## Existing Claude plugins

Levyra continues to track the project plugin configuration in
`.agents/claude/settings.json`, which is projected to native
`.claude/settings.json`. This includes the Kotlin, Chris Banes, Karpathy, Matt
Pocock, and Android reverse-engineering skill integrations. External plugins
supplement the canonical Levyra rules and `.agents/skills/`; they do not become a
second source of truth.

```bash
python3 scripts/validate_claude_bootstrap.py

python3 scripts/sync_agent_runtime.py --runtime claude --check
```

tests through its normal `scripts/tests/test_*.py` suite.
